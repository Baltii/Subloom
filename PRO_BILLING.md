# Subloom Pro billing

Free: manual subscription tracking, reminders, calendar, JSON backup and basic subscription CSV portability. Pro: statement CSV imports/recurring charge detection, transaction CSV reports, and up to 50 saved cards and wallets instead of 3 combined. Existing imported records and billing labels remain readable, editable and removable after downgrade. Existing safety/storage bounds (including 300 imported transactions) still apply. Pro does not promise unlimited storage or a bank connection.

## Billing identity and local privacy

Guest purchases use a separate persisted Supabase email-OTP session (`subloom.pro.billing.auth`). It is never assigned to the main app auth client, so verifying an email does not change the guest workspace, upload records, import records, or enable sync. Supabase creates a lightweight user/profile to own the billing entitlement. Stripe receives the verified email and opaque user ID; no tracked service names, statement contents or saved billing labels are sent to Stripe. Restore by verifying the same email on another device. Records require a separate JSON backup/restore; a billing purchase does not transfer them.

Signed-in workspaces use their own main auth identity. Guest billing access does not unlock an unrelated account. Connecting a normal account with the same email uses the same Supabase user; moving local data remains explicit. Disconnecting billing does **not** cancel renewal. Cancel in Manage billing. Account deletion expires pending checkouts and cancels the Stripe subscription before removing the auth user, under the same billing lease used by Checkout.

Entitlements are reconciled against current Stripe state, never a redirect query or client-written plan flag. The legacy `user_entitlements.plan` is not a billing authority. P-256 signed offline licenses last at most 72 hours and never beyond the current trial/paid period. They are bound to billing owner, installation and workspace cache. Tampering, wrong key, expired license and backward clock jumps fail closed. Online denial replaces the cache. Like any local application, a modified binary or deleted local clock history cannot be made a perfect DRM boundary. Account writes are also checked by Postgres. Free tracking remains usable without a network or account.

## Configuration and activation (no credentials are included in source)

1. Create a **separate Stripe sandbox** for development. This repository pins stripe-node 23.0.0 / API `2026-09-30.endive`; 23.0.1 was published inside Deno's minimum dependency-age window when implemented, so that protection was preserved. Keep the webhook snapshot version at `2026-09-30.endive` too.
2. Create recurring prices in EUR: **299 cents / month** and **2400 cents / year**, each interval count 1, per-unit, quantity 1. The server rejects other prices. Archive old prices only after planning migrations; keep configured price IDs stable while subscribers exist. No promotions, tax collection, or price-changing customer portal controls are enabled by code.
3. Configure Stripe Customer Portal: allow viewing invoices, updating payment methods and canceling **at period end**. Disable plan/quantity changes unless this implementation is extended and tested for them. Add business identity, contact/support details, privacy and refund terms in Stripe before launch. Enable Stripe's trial-ending emails, payment failure emails and cancellation communications. For card-required trials, enable payment methods compatible with this policy in Stripe's payment method configuration; Checkout uses dynamic methods and always collects a payment method.
4. Run `node scripts/generate-pro-key.mjs`. Keep `build/pro-keys/server.env` private; add its `PRO_LICENSE_PRIVATE_JWK` only to Supabase secrets. Add only the value from `public.env` to `EXPO_PUBLIC_PRO_LICENSE_PUBLIC_KEY` in public build configuration. The app compares this public key to the server's public verification key and disables new purchases if they differ. Keep a secure private backup. Rotating the key requires rebuilding clients; old offline grants stop verifying.
5. Set server secrets: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_MONTHLY`, `STRIPE_PRICE_YEARLY`, `PRO_RETURN_URL`, `PRO_LICENSE_PRIVATE_JWK`. The return URL must be a fixed HTTPS app page ending in `/pro`, with no query/hash/userinfo; never a marketing-only URL. Configure hosting to serve the Expo app for `/pro` and its query strings. Use a **restricted Stripe API key** where supported: Customers read/write, Prices read, Subscriptions read/write, Checkout Sessions read/write, Billing Portal Sessions write, Charges read, Invoices read, Invoice Payments read. No key belongs in an `EXPO_PUBLIC_*` variable or source control. Stripe webhook verification uses a separate signing secret.
6. Configure Supabase Auth SMTP and the email OTP template to include `{{ .Token }}` (a numeric code). Billing uses the existing Auth email service and its rate limits; it never uses OAuth or a magic-link callback. Confirm email verification and new email signups are enabled. The separate auth session is necessary for guest restore even when main account sync is unused.
7. Apply the migration and deploy `pro-billing`, `stripe-webhook` and the updated `delete-account` together using the repository deployment workflow. Register `https://<project>.supabase.co/functions/v1/stripe-webhook` as a required Stripe webhook. The function intentionally disables gateway JWT verification because it validates Stripe's raw-body signature. The billing function validates the bearer token using `getUser`, checks verified email, validates input, and rate limits per identity.
8. Subscribe the webhook to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.paused`, `customer.subscription.resumed`, `invoice.paid`, `invoice.payment_failed`, `charge.refunded`, `charge.dispute.created`, and `radar.early_fraud_warning.created`. Delivery failures must be retried/monitored. Event IDs are recorded only after processing, and current processor state is fetched under a database lease, so duplicate/out-of-order events do not overwrite newer state. A busy lease returns non-2xx for retry. There is no scheduler requirement for expiration: access always checks its real expiry.
9. Sandbox test every scenario below before live credentials. Use a second sandbox for CI when adding automated provider tests. Then configure a separate live restricted key, live prices, live portal and live webhook secret; rebuild the app with its public verification key. Without complete server configuration checkout is unavailable; no fake Pro grants or placeholder charges are created.

Prices shown before checkout are €2.99/month or €24/year. Eligible verified billing identities get 7 days free, with a payment method collected now. Renewal is automatic unless canceled. Returning identities pay immediately; trial history stores a one-way hash of the verified email so account deletion/recreation does not reset a used trial. That minimal anti-abuse record intentionally outlives auth deletion; processor invoices remain subject to Stripe's retention. Include this retention in the product privacy policy before launch. Tax is **not automatically enabled**: first configure registrations and decide inclusive/exclusive pricing for the markets you sell to. The app tells users to review Stripe's final total.

## Lifecycle and support

Trialing subscriptions with a recognized configured price get Pro until the trial ends. Active subscriptions also require a paid current invoice before granting their current item period; asynchronous payments remain locked until confirmed. Cancel-at-period-end retains access to that end. Past-due, unpaid, paused, incomplete and canceled states do not grant access. Full refunds on the current invoice, disputes and early fraud warnings block the billing identity pending support review; partial refunds and refunds for old invoices do not revoke a current period. A support-reviewed resolution can clear `payment_blocked` through a service/admin-only operation, after verifying Stripe. No public client can clear it. Offline revocation can take up to 72 hours, bounded by paid period. Price changes, automatic taxes, coupons, quantity changes and native store purchases require separate implementation decisions.

Native store builds default to no external purchase/manage buttons. Web, Windows and macOS use hosted Stripe Checkout. `EXPO_PUBLIC_ALLOW_NATIVE_STRIPE_CHECKOUT=true` is only for native distribution where this is permitted, such as the current direct test builds. App Store / Play releases need an in-app purchase/store policy implementation before enabling checkout; this feature does not add StoreKit or Play Billing.

Set the public verification key as a GitHub Actions **variable** named `EXPO_PUBLIC_PRO_LICENSE_PUBLIC_KEY` for CI/release installers, and in Vercel's app build environment. Set it separately in each EAS build environment (development/preview/production), since remote EAS workers use those environments. This key is public; never put the private JWK in Actions variables or Expo/EAS public environment variables. The direct Android APK workflow additionally forwards `EXPO_PUBLIC_ALLOW_NATIVE_STRIPE_CHECKOUT`; leave it unset/false for store distribution and configure direct-build environments deliberately.

## Required verification before taking real payments

- `npm run check`, `npm run check:backend`, `npm run test:backend`, and web/native bundle exports.
- Verify guest email purchase and restore without changing `useApp.identity` or uploading records. Verify main auth remains signed out, and unrelated signed-in accounts do not inherit guest Pro.
- In a sandbox, test monthly/yearly new trials with payment method, cancel during trial, period-end cancellation, returning subscribers without another trial, renewal success/failure, paused/unpaid, and portal invoices/payment updates.
- Retry Checkout concurrently and after a lost response. Verify a single subscription, pending checkout reuse and plan changes; inject duplicate and reversed webhook delivery. Unsigned/tampered/stale webhook bodies must fail.
- Test full current-invoice refund, partial/old refund, disputes/fraud flags, account deletion with pending checkout/paid subscription, and deliberate Stripe outages during deletion (must not delete and leave charges running).
- Verify offline restore ≤72h, wrong installation/owner/key, expired period, clock rollback, online revocation and returning from the browser to Check purchase. A browser success URL alone must never grant Pro.
- Verify free 3-method limit on local and authenticated writes, editing/removing existing over-limit methods, locked imports/CSV report, and free JSON backup/manual tracking/reminders. Rebuild and test on a real Windows laptop and native devices; bundle exports alone do not prove device behavior.

The sandbox credential check above supplements the database/processor mocks and cryptographic tests. It does not replace a completed sandbox payment, signed webhook delivery, or the full app/device acceptance run. No live payment has been performed.
